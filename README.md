# Mercury

A Windows-first desktop assistant with an orange-and-black interface for chatting with local and cloud models and planning software changes. **Chat** lets you select an individual model, stream replies, switch models, stop generation, and reopen saved conversations. **Projects** uses Planner to inspect your project and prepare a plan for approval. Main then implements and verifies it; every shell command requires approval. In chats and project implementation, Main can delegate bounded analysis to a read-only Subagent and act on its findings.

## Requirements

- Windows 10 or newer, Node.js 24+, and npm.
- A running Ollama or LM Studio server, an eligible ChatGPT account, or an OpenAI / Claude API key. A model that supports tool calls is required for coding.

## Run

```powershell
npm install --offline=false
$env:PLAYWRIGHT_BROWSERS_PATH = Join-Path (Get-Location) '.build-resources/browser-runtime'
npx playwright install chromium --only-shell
npm start
```

Mercury opens in **Chat**. Choose **Local**, **OpenAI**, or **Claude** at the bottom of the message box, then select a model in the adjacent dropdown and send a message; no project is needed. The refresh icon next to the picker requests a fresh model scan. Enter sends a message, and Shift + Enter adds a line. Use **New chat** to start fresh, or select a saved conversation in the sidebar. Separate chats can generate concurrently; only one response runs within each chat. Chat has no project tools or command access. Project agent runs remain exclusive with chat generation.

Mercury keeps an internal active/queued request tally for each provider/server/model, available as `snapshot.modelRequests`, plus `activeChatIds`. FIFO queues dispatch only when a slot opens. LM Studio's discovered `loaded_instances[].config.parallel` sets the capacity; if unavailable, Mercury allows four requests. Ollama conservatively allows one unless you configure a matching override under **Model settings → Agent models and context → Concurrent requests per model** (1–32). These are Mercury's dispatch limits, not a change to the server's configuration. Discovery preserves reported capacities through restarts. The tally covers requests from this Mercury process, not traffic from other clients. Stop cancels only that chat's active or queued work; success, failures, fallback, and cancellation release slots. Queue waiting does not count against the thinking watchdog, and background completion never changes the selected chat. [LM Studio capacity metadata](https://lmstudio.ai/docs/developer/rest/list), [Ollama concurrency configuration](https://docs.ollama.com/faq).

Drop files anywhere in Chat. A drop overlay appears while dragging, and selected files appear as removable chips before sending; there is no attachment button. Ctrl+O (Cmd+O on macOS) while focused in Chat opens the file chooser as a keyboard fallback. Text dragging still works normally, and dropping a file elsewhere cannot navigate the app away. Wait for a response in the selected chat or an upload to finish before adding files; other chats do not block uploads. Each message supports up to eight regular files, each up to 25 MB, with a maximum of 300,000 extracted characters per file. Text previews are included in the selected model's prompt and longer content is available through `read_file`. Uploaded documents are source material, not instructions.

Common content readers include PDF, DOCX, PPTX (including notes), XLSX/XLSM cells and saved formulas/results, ODT/ODS/ODP, EPUB text, RTF, and text/code/data files in UTF-8 or BOM-marked UTF-16. Recognized text formats can fall back to Windows-1252 with an encoding note. ZIP/TAR archives provide member listings; GZIP text can be decompressed within limits. Office macros, embedded scripts, and uploaded programs are never executed. Office extraction covers text/tables/cells, not exact layout or embedded visual interpretation. EPUB reading order is best-effort.

Image attachments are sent as actual image data: Ollama receives base64 `images`, LM Studio receives OpenAI-compatible `image_url` content parts, OpenAI receives Responses `input_image` parts, and Claude receives base64 image blocks. A vision-capable model and a working vision encoder are required. Up to eight recent user images are reattached on follow-ups from their saved conversation files; base64 is not stored in chat history or counted as ordinary text context. Native PNG/JPEG/WebP images within the size limits are sent unchanged; other decodable raster formats and larger images are normalized to at most 2048 pixels per side, using the first frame/page. The source safety limit is 20 megapixels and the combined encoded-image budget is 24 MB. Files remain saved at original quality. Provider image-token limits still apply.

If the server explicitly reports that image input is unsupported, Mercury retries once with the extracted text and shows a visible fallback notice. This is remembered for that connection/model for five minutes. Authentication, rate-limit, corrupt-image, context-limit, and generic network errors remain errors, not misleading text fallbacks. No image fallback is retried after streamed output/tool activity or after Stop. Servers that silently ignore images cannot be reliably detected; configure a vision-capable model in the server. No image-generation model is required.

Local English OCR is bundled with its engine and language data: PNG, JPEG, BMP, TIFF, and other decodable image formats can supply fallback text without an OCR service. Scanned PDFs use OCR for up to ten image-only pages; PDF inspection covers up to 200 pages. Images are limited to 20 megapixels, PDF OCR pages to eight megapixels, and each OCR job to 45 seconds. Recognition can contain errors and does not interpret scenes or chart graphics; that requires actual image input to a vision model. For proprietary, encrypted, damaged, unsupported, audio/video, or other binary files, Mercury retains the file and supplies an explicitly labeled metadata-only report (type/size/hash/header/bounded printable strings) rather than pretending it decoded the content. File cards and `read_file` results state text-extraction limits, separate from model vision. Oversized extracted text is visibly truncated; encrypted archives, external XML entities, and excessive archive expansion are not decoded.

Ask a model with tool-call support to create the file you need. Successful creation displays a file card with **Save filename**. The Save dialog chooses the destination; the file cards and attachment references survive restarts. Files and extracted text are retained under the app's `chat-files` data directory. Selecting a cloud model sends extracted attachment content and supported image payloads to that provider. Models or servers without tool-call support can read the included previews but cannot request file creation.

Standard output tools run locally and do not need an image-generation model:

- `create_pdf`: formatted PDF from Markdown, with math and highlighted code.
- `create_document`: real Word DOCX with headings, emphasis, lists, tables, and code.
- `create_spreadsheet`: real Excel XLSX with named sheets, typed numeric/boolean/text cells, a styled header, frozen header row, and column widths. The first row is the header. Formulas entered as strings remain literal text; the app does not execute spreadsheet formulas.
- `create_presentation`: real PowerPoint PPTX with slide titles, body text, bullet lists, tables, and speaker notes. Large tables are split into continuation slides.
- `create_graphic`: SVG, PNG, or JPEG from pixel-based rectangles, circles, lines, paths, and text. This supports programmatic diagrams/charts/illustrations, not photorealistic image synthesis.
- `create_archive`: ZIP from text entries or existing conversation file IDs, including generated binary documents and graphics. Only conversation files can be included, and member paths must be relative.
- `create_file`: Markdown, source code, CSV/TSV, valid JSON, HTML, XML, SVG, LaTeX, complete RTF source, and other UTF-8 text. Binary extensions require a dedicated format tool; renaming text never produces a fake Office document or image.

Chat instructions favor creating files proactively for substantial reports and analyses, long explanations (roughly 800+ words), complete source files, and large datasets (roughly 20+ rows), even without an explicit file request. The model chooses PDF for readable reports and Markdown/code/CSV/JSON for editable or machine-readable work, then gives a concise summary beside the file card. Short answers stay in chat, and an explicit inline-only or format preference takes priority. A requested file should be created directly rather than replaced with an offer or a script for the user to run. Document contents remain source material; embedded instructions do not authorize tool calls.

PDF generation renders Markdown into styled headings, paragraphs, lists, real tables with repeated headers, highlighted code blocks, and KaTeX mathematical notation. Chromium prints page numbers with automatic pagination; short code blocks stay together when space permits. Math fonts are embedded for offline packaged builds. Model HTML is sanitized, external images are placeholders, and document scripts/network requests are blocked. Supply a complete Markdown document in `create_pdf.content`, not a fenced block wrapping the whole document. No Python or separately installed PDF plugin is required.

Responses render Markdown: headings, bold, italics, underline (`<u>text</u>`), strikethrough, quotes, nested lists, checklists, tables, links, highlighted code with a Copy button, and math using `$...$` or `$$...$$`. Model HTML is sanitized; external images are not loaded. Web links open in the system browser only when clicked.

While a response is in progress, Mercury shows a compact **Thinking ⌄** row and elapsed time. Click the row to expand the live reasoning; it starts collapsed and stays as you leave it while the answer arrives. Models can return reasoning through Ollama's `thinking`, LM Studio's `reasoning_content`, or a leading `<think>` block. Mercury does not fabricate reasoning for models that do not provide it. Reasoning is saved with the response and excluded from later conversation prompts. Stop works during both thinking and answering.

Generation now uses a rolling two-minute inactivity window, not a two-minute thinking lifetime or ten-minute provider lifetime. Nonblank reasoning, answer text, and streamed tool-call progress renew it; queue waiting is excluded, while empty heartbeats/whitespace do not count as useful progress. Continuing fresh reasoning is not cancelled at 30,000 characters; the saved/displayed reasoning retains its latest 100,000 characters to bound memory. Repetition recovery requires a phrase repeated six times AND a heavily duplicated recent window (65% repeated phrase windows), so repeated headings among fresh analysis are allowed. A stalled generation can retry once before any answer text; a stall after an answer starts preserves it without replaying/discarding it. Stop never retries and completed tool actions are not replayed. Servers can still impose their own limits, and silent internal prefill cannot be distinguished from a stalled server without a reported progress signal. Context, output-size, approval, and external-service resource limits are separate explicit safeguards, not total task timeouts.

Open **Model settings** to configure Planner, Main, and Subagent models (unset Planner/Subagent selections use Main). The app scans running Ollama and LM Studio servers on this computer, saved connections, and reachable Tailscale, WireGuard, and ZeroTier peers on their standard ports (`11434` and `1234`). Each role has its own context setting and an accessible description. Connection boxes list models by device or cloud account; only responding servers with models are shown, and local servers expose concurrency controls. Unavailable/empty servers stay saved but are hidden. A global empty state appears only when no models are available. ChatGPT sign-in and API keys have separate sections; Connect with Codex is an experimental connection through an installed Codex app or CLI. It uses Codex-managed ChatGPT sign-in in Mercury’s own profile; it is separate from Mercury’s direct ChatGPT connection and API keys. Choose **Other…** in a model dropdown to add a custom address or port, including servers the scan misses. An optional API token can be entered there and is stored using Windows protected storage. The shared LM Studio server at `http://100.80.53.57:1234` is included in this prototype's saved connection defaults.

Open **Model settings → Cloud accounts** to connect an account. **Continue with ChatGPT** opens the system browser for the official OAuth flow; eligible accounts can grant ChatGPT plan usage. You can add multiple ChatGPT accounts, reconnect them, or disconnect them. Access and refresh tokens stay in the main process and are encrypted with Windows protected storage. OpenAI API keys are also supported with separate API billing.

Claude connects using a **Claude Console API key**, with separate API billing; this option does not sign into a Claude chat subscription. The app discovers models from each account instead of hardcoding model names, so Fable, Astra, or other models appear only when the account's model catalog exposes them. Cloud models support streamed text and tool calls for project agents. Interrupted or failed cloud streams are reported as failures, including usage limits received after streaming starts.

Official integration references: [ChatGPT sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [ChatGPT models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference), and [Claude authentication](https://platform.claude.com/docs/en/manage-claude/authentication).

Model discovery is shared between Chat and Settings and cached in SQLite across restarts. Successful lists are reused for 30 minutes; an empty result is retried after one minute. The saved catalog is shown immediately across settings opens and app restarts. Opening Settings or the app checks connections quietly in the background; successful checks do not show a spinner or clear selections. Lost connections show a notice and disappear from settings. The Refresh button explicitly rescans. Changing connection details or credentials, or encountering a connection/model-availability error, invalidates it. Changing model roles does not invalidate the discovery cache. Concurrent discovery requests share one scan.

For coding, select **Projects**, open a folder, describe a task, review the generated plan, and use **Approve and implement** when it is ready. The agent can read and create Markdown, source code, JSON, and other UTF-8 text files, read selectable text from normal PDFs, and create simple text PDFs. File edits appear in **Changes**. Commands require approval showing the exact text and working directory.

## Built-in capabilities and plugins

Every chat includes Playwright browser tools and a bundled Chromium headless runtime. No separate browser installation, search API key, or project is required. `browser_search` searches public pages (with alternate engines when challenged), `browser_open` reads a rendered webpage, `browser_read` pages through longer text, `browser_click` follows returned link URLs, and `browser_close` releases the session. Browser tools return source URLs for citations and log their actual success/failure under **Tools used**. Browser contexts/cookies are isolated per chat, retained for five idle minutes, and closed on Stop or app exit. Up to 24 contexts are allowed. Websites can still block automation, require login, or have unsupported content; challenges are not bypassed and snippets are not treated as verified source pages.

The collapsible right-hand context panel has **Files** and **Browser** tabs. Files include current uploads and artifacts from the selected conversation: click **Preview** on a file card or select it in the panel. PDFs render actual pages with previous/next controls, raster images display directly, Markdown is sanitized and formatted, and other files show extracted text or metadata (not a native Office layout). Nothing previews as executable HTML. Save remains available separately. Playwright activity automatically reveals a live, read-only image of that chat's actual isolated viewport; it refreshes about once per second while visible. This display does not navigate a duplicate browser, grant control permissions, add screenshots to model context, or extend the browser session's idle lifetime. Shrink hides the preview and stops refreshing until reopened from the slim side rail. Updated executable: `out/mercury-context-panel/Mercury-win32-x64/Mercury.exe`.

Browser navigation/subresources are restricted to public HTTP/HTTPS addresses. Private/LAN/loopback/link-local/metadata endpoints, file/data/JavaScript URLs, credentials in URLs, non-GET requests, WebSockets, service workers, popups, dialogs, and downloads are blocked. No model-supplied JavaScript, shell, selectors, forms, purchases, or personal browser cookies are exposed. Fixed internal page evaluation reads text and links only; this is a browsing capability, not unrestricted website automation. DNS checks are defense in depth, not an operating-system security sandbox. The coding agent's separate approved command workflow remains unchanged.

Visual/game browsing adds `browser_screenshot` (actual JPEG pixels passed to vision models and saved as a file card), frame/canvas and embed/Ruffle inspection, and bounded `browser_wait` for loading/animation. Text-only models receive a truthful text fallback and must not guess unseen canvas state. `browser_enable_controls` asks approval for the current page/embedded origins; only then can `browser_pointer` click 1280×900 viewport coordinates or `browser_press` send up to 100 game keys with optional 0–1000 ms spacing. Only arrows/WASD/digits/Space/Enter/Escape/Backspace/Shift are supported, not arbitrary typing or OS shortcuts. Permission expires on session closure or an unapproved origin change. Network restrictions remain unchanged: controls do not enable logins, purchases, forms, downloads, or arbitrary scripts. Canvas/Flash games may expose no useful DOM text even though the page is accessible; use screenshots instead of trying text proxies. No claim of full game completion is implied by tool availability.

Browser navigation observes document/script/stylesheet transfer progress and uses a 30-second inactivity window, not a 25-second total loading deadline. A load that stalls after committing preserves and reports a partial page when readable. DOM/frame inspection and screenshots also have inactivity guards; explicit Stop closes that chat's browser. Browser state is retained for five idle minutes between turns. Persistent ads or a site's own code, unsupported multiplayer/WebSocket behavior, browser/server failures, and site access controls can still limit a game.

Chat's built-in MCP plugin finder uses the [official public MCP Registry](https://registry.modelcontextprotocol.io/) through `discover_plugins`. It returns relevant registry entries, immutable short-lived candidate IDs, transport details, limitations, and installed plugins. `install_plugin` asks for in-chat human approval before downloading/starting third-party code or connecting to a new service. It supports no-configuration Streamable HTTP servers and exact-version public npm Node.js MCP packages, with lifecycle scripts disabled. Required keys/OAuth, arbitrary arguments, Python/Docker, legacy SSE, and other transports require additional setup and are not silently guessed or installed. A registry listing is not a security endorsement.

Approved installation validates MCP initialization and discovers the real tool schemas before saving an active plugin manifest under the app's `plugins` data directory. Installed plugins are available to other chats and survive restarts. Use `plugin_list_tools` to inspect an installed plugin and `plugin_call_tool` to invoke it. Each third-party startup/inspection or invocation asks separately for approval showing the endpoint/package and arguments. Denial blocks further third-party approval attempts until a new user message. Stop, errors, stale/fabricated/cross-chat candidates, and failed installation never grant permission. npm servers run with the user's OS permissions: they are NOT sandboxed and can access files/network; approve only trusted code. Remote servers receive approved arguments. Mercury does not forward model credentials to plugins.

Tool actions have explicit safety limits of 256 per response and 128 model/tool rounds, not timeouts. Only the latest four browser screenshots remain in model context, while saved file cards persist. Plugin HTTP responses are bounded to 2 MB and model-facing results to 50,000 characters. Browser page text is paged and bounded. Pending approvals time out after five minutes and never occupy model inference slots. These tools are included for every provider, but the chosen model must support tool calling and may still choose tools incorrectly. See [Playwright browser requirements](https://playwright.dev/docs/browsers) and [MCP local-server security guidance](https://modelcontextprotocol.io/docs/develop/connect-local-servers).

Project agents retain their separate informational `discover_plugins` capability. It searches the built-in capability registry and declarative project-local manifests in `.mercury/plugins/*/plugin.json`, matching names, descriptions, and optional `keywords`. Those project manifests are descriptions, not executable MCP installations. A minimal project manifest looks like:

```json
{
  "id": "my-plugin",
  "name": "My plugin",
  "description": "Helps with a particular kind of task.",
  "keywords": ["task", "automation"]
}
```

## Data and limitations

Chats, project sessions, and settings are stored in `state.sqlite`, outside the selected project. Mercury continues using `%APPDATA%/Local Plan Agent/` to preserve data and protected tokens from earlier builds. Model inference goes only to the selected local server or cloud provider, without automatic cloud-model fallback. Browser tools contact requested public websites/search engines; plugin discovery contacts the public registry; approved plugins contact their services or npm and may execute local code. Selecting a cloud model sends the conversation and relevant tool results to that provider. Mercury does not download models or start a model server. Tailscale peer discovery requires its command-line client; WireGuard host routes and Windows VPN neighbor entries are checked when available. VPNs that do not expose peer addresses require **Other…**.

Command approval controls whether this app launches a command; it is not an operating-system sandbox. Planning agents have only read/search tools. Project coding edits require a file hash so changes made in another editor are not silently overwritten; project workspace tools retain their 512 KB text/simple-PDF limit. Chat's broader readers and native document tools operate on conversation attachments up to 25 MB with the extraction limits described above. After an interruption, resuming project work requires an explicit click and does not automatically replay an uncertain tool result.

The model/server combination matters: a tool-use check runs before implementation. Some models may produce a useful plan but lack reliable tool calling for coding. Live model compatibility and hardware performance must be checked on the target machine.
